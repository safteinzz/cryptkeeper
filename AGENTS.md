# AGENTS.md

Working brief for an AI coding agent; people read README.md.

`cryptkeeper` is a Rust CLI, binary `ck`, that locks and unlocks whatever is encrypted on the machine from wherever you stand: gocryptfs folders, LUKS drives and image files, and age files. It shells out to the real `gocryptfs` and `fusermount3`, `udisksctl`, and `age` (or `rage`), and never touches ciphertext itself, so every vault stays usable without ck.

## Invariants and gotchas
- The binary is bare-first: bare `ck` with stdin and stdout on a terminal opens the terminal UI (`src/tui/`), and otherwise prints `vault::nearest` as `ls` rows; `--help` carries both as the two lines under Ways to run it. The vocabulary `open`, `locked`, `dead`, `exposed`, `missing` and the kind words `gocryptfs`, `luks`, `age` are defined in `AFTER`; a new state or kind word goes there in the same change.
- Every command that changes something takes `-n`, and a dry run prints exactly the lines the real run would: each command checks everything first, skips only the action and its registry write under `dry`, then prints. A new command keeps that shape. The one exception is the first `unlock` of a LUKS vault never mounted before: udisks picks the mountpoint, so the dry run names the drive or image where the real run names the mountpoint; `--help` says so on `unlock -n`.
- `unlock` has no `--all` on purpose, since every vault asks for its own password; `--help` says so. `lock --all` carries on past a vault that refuses and exits 1 at the end if any did, but stops at a Ctrl-C rather than ask the next vault's password; every child that takes the terminal goes through `run::take_terminal`, which clears the Ctrl-C flag first, so one cancel never makes a later failure read as cancelled.
- `forget` drops any vault from the list, missing or not: named as `ls` prints them (a leading `~/` is expanded, and the encrypted side matches too), or with none named, picked by number at a prompt (numbers on stdin, empty cancels). `clear` drops every `missing` one and takes nothing; the name says it tidies leftovers, so it must never grow a way to drop a present vault.
- A gocryptfs vault is any folder holding `gocryptfs.conf`. Its view is, in order: the one the list stores, `<name>` beside a `.<name>` folder (what `ck init` makes), the mountpoint `/proc/self/mountinfo` gives it while open (gocryptfs names the mount after its encrypted folder), else none (`Vault::view` empty) until `unlock --at <dir>` gives one, which the list then keeps. `unlock` without a known view refuses and names `--at`, with the folder shell history last opened it at when `scan::opened_before` finds one: history is only ever a hint in a message or a form, never acted on. A vault whose `gocryptfs.conf` was moved elsewhere (`-config`) is not looked for. `vault::find` walks up from the start folder and at each level takes that folder itself when it is a cipher, a view (listed, beside its `.<name>`, or mounted) or a listed LUKS mountpoint, else every vault right inside it: folders holding `gocryptfs.conf`, `.age` files with an age header, and listed vaults opening there; several is an error that names them, never a guess. A start path that does not exist still resolves when its `.<name>` or `<name>.age` sibling is a vault, so a deleted view reopens by name.
- `vault::resolve` is what a typed path goes through: a name in the list first (so a locked drive's vanished mountpoint still works), then `UUID=<uuid>`, a block device, a file (an age view, an age file, a LUKS image), or a folder to walk up from. A file that is none of these is refused, never walked up from.
- Bare `ck` piped prints `vault::nearest` as `ls` rows: every vault at the nearest level, so a folder holding several shows them all instead of failing the way `find` does for `unlock` and `lock`. The terminal UI starts its cursor on that same nearest vault.
- `ls`, `ls --json`, bare `ck` and the terminal UI all build their rows with `listing`, from the same reads and nothing else: `ls` adds, set apart after the listed vaults, every vault `scan::found` finds that the list does not hold (every open gocryptfs, and every gocryptfs folder, `.age` file and LUKS image file bigger than 16 MiB (so a header backup, which is exactly that and holds nothing to open, is skipped) under home, by a walk at most six folders deep and 1.5 seconds long that skips dot folders and `node_modules`), then every LUKS device it does not hold (`luks::drives`, from sysfs and the udev database only, never udisksctl or polkit, so nothing can hang or prompt). A found vault's note says how to add it. A drive's note says whether ck would ever lock it: the disk the system runs from (anything `luks::refusal` calls system, swap or stacked, followed down through LVM to its mounts) and one unlocked outside ck are never offered a lock. `--json` writes the fields kind, state, name, cipher, view, where, timeout, identity, listed and note; `--help` states them as fixed, so renaming one is a breaking change.
- `ck check` only reads: versions from `gocryptfs -version`, `fusermount3 -V` and `age --version`, `/dev/fuse` from its mode and the user's groups without opening it, `udisksctl status`, `pkcheck` for the udisks unlock, mount and loop-setup actions (0 allowed, 1 refused and so `blocked`, 2 a password each time, which is what an ssh session gets and still counts as `ready`, its detail saying so and naming the sudo setting), and `$XDG_RUNTIME_DIR` through `age::runtime_problem`, the same rules `unlock` enforces. Every child runs through `run::bounded`, killed after five seconds. Its state words are `ready`, `missing`, `blocked`, `unchecked`, defined in `AFTER`; it exits 1 unless all are ready, and the fix names this distro's install command from `/etc/os-release`.
- `vault::find` and `scan::found` never look into a mountpoint (read from `mountinfo` before any stat), because a walk through `/media` must not stat a dead FUSE mount and hang; a symlink is followed only to a dot folder, and `scan` follows none.
- `init` on a name that is not an existing file makes a gocryptfs vault; on an existing regular file it makes an age vault (`age::init`: encrypted to a temp file beside it, checked as `lock` checks, synced, put in place with a hard link so nothing there is replaced, and only then the plaintext deleted, unwiped). It refuses a symlink, anything but a regular file, a file with other hard links (deleting one name would leave the plaintext under the others), an existing `<file>.age`, an age file, and ck's own open copies. `init --luks PATH` makes a LUKS vault (`luks::init`): a new image file of `--size` (sparse, at least 32M, written with a unit since a bare number is refused), or with `--wipe` a drive, refused anyway when it is mounted, built on, swap, read-only, a device-mapper device or a disk split into partitions (`luks::in_use`). `cryptsetup luksFormat --type luks2 --verify-passphrase` writes the header (as the user for an image, through `sudo` and without `-q` for a drive, so cryptsetup still asks for an uppercase YES), then `sudo cryptsetup open` under `ck-new-<pid>`, `sudo mkfs.ext4 -E root_owner=<uid>:<gid>` and `sudo cryptsetup close` make the filesystem, which only root can, and a failed image is removed again. Its passwords are cryptsetup's and sudo's own prompts, as every other tool's are. For gocryptfs it runs `gocryptfs -init` without `-q`, because that is what prints the master key, the only recovery after a forgotten password, and gocryptfs shows it once. A failed or cancelled `init` removes only the folders it made itself.
- `lock` with no path falls back to the only open vault only when no vault exists anywhere above the current folder; beside several it fails and names them, like `unlock`. `vault::nearest` returns `None` for that case so the two are told apart.
- `is_mounted` counts only a `fuse.gocryptfs` mount on the view, so another filesystem mounted there never reads as the vault being open.
- Every message names a vault by its view (`Vault::name`: a LUKS vault never mounted yet is named by its drive or image). The gocryptfs cipher path appears only in `init`'s already exists error; age errors about the file's own content name the `.age` file, which the user knows.
- `$XDG_CONFIG_HOME/cryptkeeper/vaults` (usually `~/.config/cryptkeeper/vaults`) holds `kind\tcipher\tview` per line, absolute, with a fourth field for an age vault's identity file; a two-field line is gocryptfs, which is how the list under `$XDG_CONFIG_HOME/egc/` (this tool's old name) was written. That old list and its `settings` are read while the new file does not exist, and never written or removed. `registry::check_storable` refuses a path with a tab or newline before anything is made. A file that exists but cannot be read is an error, never an empty list, because the next save would wipe it; saves go through a temp file and a rename. A symlinked path is resolved before it is stored: `vault::settle` resolves every detected vault's encrypted side through its symlinks (a symlinked dot folder or `.age` file included, so a lock writes the real file) and its view's folders, keeping the view where it was found, and `vault::nearest` resolves the parent of a view that does not exist yet, so one vault never gets two lines; `remember` updates a line in place when a LUKS mountpoint or an age identity moved. `init`, `unlock` and `add` add to it; `lock` never does; `forget` and `clear` remove lines and never touch a vault itself; `delete` removes a vault and its line. A vault on an unplugged drive stays listed as `missing`.
- Mounted is not open: a gocryptfs that died leaves the mount listed in `/proc/self/mounts` with every read failing, so `unlock` checks `read_dir` and clears a dead mount with `fusermount3 -u -z` before remounting. Lazy unmount is only ever used on a dead mount.
- `unlock` passes `-nosyslog` only when `/dev/log` is missing (WSL without systemd, a container): there gocryptfs's switch to syslog fails, prints five "Unix syslog delivery error" lines and then drops every later warning, a corrupt block included, while with syslog present its messages belong in the journal as before.
- `unlock -t N` (N at least 1, since gocryptfs reads 0 as never) passes `-i Nm` to gocryptfs, which unmounts only after N minutes with no activity and no open files. `ls` reads the timeout back from the gocryptfs process's `/proc/<pid>/cmdline`, so no state file exists to drift. `-t` on another kind is refused.
- ck's own prompts are `forget`'s numbers, `init`'s name and the terminal UI, and each has an argument or a pipe that skips it. `init` asks only when stdin is a terminal, because a piped stdin carries the password for gocryptfs and a name prompt would swallow it.
- `ck add <PATH>` puts the vault it names in the list as it is and opens nothing: a vault found, or a drive ck never touches, which then shows as the user's own. A row names a LUKS vault never mounted by its device (`Vault::shown`), the name every command takes it by.
- `ck delete <PATH> --yes` removes a locked vault for good: a gocryptfs vault's encrypted folder (only while it still holds `gocryptfs.conf` and is no mountpoint) and its view when empty, an `.age` file and a link left at its view, or a LUKS image file, then its line in the list. It refuses an open vault (lock it first), a missing one, a drive, a path that is only in or beside a vault (`vault::is_named_by`, so a folder inside one or the folder holding it never deletes it the way `unlock`'s walk up would find it), and without `--yes`.
- `ck passwd` changes a vault's password through its own tool: `gocryptfs -passwd`, `cryptsetup luksChangeKey` (as the user for an image, through `sudo` for a drive, and refused for an open device `luks::refusal` would refuse to lock, so the system disk is never touched), or for an age passphrase file an unlock with the old one and a lock with the new one; an age file locked to an identity has no passphrase and is refused. `ck backup` copies a gocryptfs vault's `gocryptfs.conf` (mode 0600) or a LUKS header (`cryptsetup luksHeaderBackup`, handed back to the user with `sudo chown` for a drive) to `--to`, or to a new `<name>.gocryptfs.conf` or `<name>.luks-header` (numbered when taken) under `$XDG_DATA_HOME/cryptkeeper/backups`, and never overwrites a file; an age file is refused, since it has no header apart from itself.
- `ck edit` (age only) and `ck shell` (any kind) unlock through the same `unlock_one` as `ck unlock`, run `$VISUAL`, else `$EDITOR`, else `vi` through `sh -c` (so `code --wait` works), or `$SHELL`, else `/bin/sh`, in the view (an age file's folder) with `CK_VAULT` set, then lock through `lock_one`, only when they themselves unlocked it; an open vault is left open and says so. A dry run prints the unlock and lock lines the real run would.
- A lock that fails because the unmount said busy lists the user's own processes holding the view (`mounts::holders`: the `cwd`, `root` and `fd` links in `/proc`, read with `readlink` and compared as paths, never a stat inside the mount), five at most, then what to do; with none of the user's, it says so.
- ck's own result lines go through `say!`, which prints them, or while the terminal UI runs an action, keeps them for its status line (`out::capture`). Printing rows for people (`ls`, bare `ck`, `forget`'s list) stays a plain `println!`.
- Password prompts belong to gocryptfs, udisksctl and age: their stdin and stdout are inherited, and outside the terminal UI their stderr too, so their own error lines print above ck's one line. Ctrl-C or Ctrl-\ at that prompt hits ck too, so `run::catch_interrupts` catches both with signal-hook (caught, never ignored, since a child inherits an ignored signal and could not be cancelled) and the runner reports `Cancelled`, which is what lets `init` remove the two empty folders it made; an empty `.<name>` left by a harder kill is reused by the next `init`.
- `run::take_terminal` returns a guard that, when dropped after the child, puts back the terminal settings and ck's ownership of the terminal as they were before it (only when ck's group was the foreground one): a password prompt killed by Ctrl-C leaves echo off, which the terminal UI's raw mode would otherwise save and restore on exit, and an interactive shell killed outright leaves its own process group in charge, which stops ck with SIGTTOU (blocked while it takes the terminal back). Every child that may ask on the terminal takes it through this, `run`'s runners and the `udisksctl` and age children alike.
- A line in the vault list ck cannot read is written back as it was on every save, so a newer ck's line or a hand edit is never dropped.
- A gocryptfs mount, the editor and the shell run through `run::foreground`, which never puts anything between them and the terminal: the mount's daemon keeps the stderr it was given, which a pipe nobody reads any more would block or kill, and a shell is interactive only with a terminal on its stderr. A mount's failure is therefore said in ck's words, from the exit codes `man gocryptfs` lists: 12 is a wrong password, 10 a view with files in it.
- The terminal UI has three tabs: Vaults (the list, then under a `found on this machine` heading the cursor steps over, every LUKS drive it does not hold, from `luks::drives`) This machine (`check::all`), and Settings (`settings::Settings::rows`: Drives through, `udisks` or `sudo`, and the new vault name), with a detail panel at 96 columns and wider. In Settings, `↵ change` steps a picked setting or opens a one-field form for a typed one (checked as it is typed), `d default` puts it back as ck ships it, and every change is written to the file at once, so nothing is left unsaved; changing Drives through runs the checks again. That section also holds what `scan::found` finds, and a vault leaves it once `↵` unlocks it, since that lists it; `↵` on a gocryptfs folder whose view is not known opens the open-at form first, filled in from shell history when it has the folder. Every action runs through the command's own function (`commands::unlock`, `lock`, `edit`, `shell`, `init`, `forget`) under `out::capture`, and the screen steps aside only when a program is about to take the terminal, through `out::hand_over`, which `run::take_terminal` calls. A new child that may ask on the terminal must go through `take_terminal`, or it prompts under a screen in raw mode. While the UI captures, `run::prompting` relays the child's stderr and keeps a copy (`out::hear`); a failure is the status line when it is one short line of ck's, else an alert holding the `ck` command, the program's last five lines without its prompts, and ck's line. After a gocryptfs vault is made it waits for a key on the plain terminal, where gocryptfs printed the master key once. It reads the rows again every two seconds with the same reads as `ls`, runs `ck check`'s probes and `scan::found` together on a thread, off the loop, only at start and on `r`, catches Ctrl-C for the whole run (`run::catch_interrupts`) so a cancelled prompt never leaves the terminal raw, and restores the terminal on every exit and on a panic (a panic hook).
- The terminal UI's own keys are `↵ unlock/lock` (unlock a locked, dead or missing vault, lock an open one ck may lock; on a vault found it only says `a` adds it, so Enter never lists one by surprise), `a add` (`ck add`, shown only on a vault found), `s shell`, `p password` (`ck passwd`) and `b backup` (`ck backup`), and on This machine `↵ install`, which offers (a cyan Yes/No box) to run the install `Check::command` takes from a missing kind's fix, handed the terminal like a password prompt, and checks again after. Of the shared words, `c create` opens a picker (encrypt a file, a new encrypted folder, a new LUKS image or drive, or one you already have, which runs `ck add` and opens nothing) and then that one's form, `e edit` is `ck edit`, shown in the footer only on an age file, `f forget` is `ck forget` (a project key, since `d` means delete and nothing else), and `d del` is `ck delete` behind a typed gate where Enter does nothing until the vault's short name is typed (a LUKS vault's image file name, else the last part of the name the list shows), while the body names it in full; `d` on a drive, an open vault or a missing one says why not instead. Each form shows the `ck` command it will run as it is typed, and while the input does not fit (`Form::check`: a path that is missing or already there, a folder that is not empty, a size without a unit or under 32M) says why in its place, in yellow, and refuses to submit; formatting a drive goes through a typed gate, where Enter does nothing until the drive's device name (`sdb1`) is typed. On the LUKS form's path, Ctrl-O opens a picker of the drives `luks::formattable` lists (disks and partitions with media, at least 32 MiB, not LUKS already, never loop, RAM, optical or device-mapper ones, and nothing `in_use` refuses), each with its size, bus, filesystem and label, so the person sees what formatting it would wipe. Vaults names a kind by what it is (`folder`, `drive`, `image`, `file`) and This machine by what it opens (`Encrypted folders`, `Encrypted drives`, `Encrypted files`); `ls`, `--json` and `ck check` keep the kind words.
- `ck completions <shell>` prints clap_complete's dynamic registration, the same script `COMPLETE=<shell> ck` prints, and `main` answers its callbacks first thing (`CompleteEnv`). Vault arguments complete from `registry::load` alone, never a state read; `--add` appends one line to the shell's startup file only when no line there loads it already.
- `lock` refuses when the current folder is inside the view, since the shell's cwd alone keeps it busy. After `unlock` from inside the view, the shell still sees the empty folder underneath until `cd .`.

## LUKS
- `luks = sudo` in the settings file (Drives through in the Settings tab; off by default) swaps udisks for `sudo`: `sudo cryptsetup open <drive or image> luks-<uuid>` (cryptsetup serves an image from a loop device that goes when it closes), `sudo mkdir -p` and `sudo mount` on `/run/media/<user>/<label or uuid>` (with `uid`, `gid` and `umask=077` for FAT, exFAT and NTFS, which keep no owners), and to lock `sudo umount`, `sudo cryptsetup close` and `sudo rmdir` of that folder. sudo asks for a password once and remembers it, where polkit over ssh asks at every step; `need` and `ck check` then ask for cryptsetup and sudo instead of udisks. The records, refusals and states are the same either way, read from sysfs and mountinfo.
- By default everything goes through `udisksctl` (`loop-setup`, `unlock`, `mount`, `unmount`, `lock`, `loop-delete`), so no root is needed; state is read from `/sys/class/block` (holders, `dm/uuid`, `loop/backing_file`), `/proc/self/mountinfo` and the udev database in `/run/udev/data`. A drive is stored as `/dev/disk/by-uuid/<uuid>`, so a replugged stick is the same vault and an unplugged one reads `missing`; an image file is stored by its path and served by a loop device ck sets up and deletes again.
- ck locks only what its own `unlock` opened: `$XDG_STATE_HOME/cryptkeeper/opened` holds `boot_id\tuuid\tloop` for each, and a line from another boot vouches for nothing. A device found locked drops its line. `luks::refusal` is the one gate before any lock, and also refuses a device mounted on a system folder, holding swap, with anything stacked on it (LVM), unlocked outside ck, or mounted anywhere but its view. A device already unlocked outside ck is refused by `unlock` too, and listed only by `ck add`, which opens nothing; listed, it is still never locked, its passphrase never changed and it is never deleted (`luks::untouchable`, which `listing` uses to mark it not lockable and `passwd` checks).
- A device that unlocks but will not mount is locked again (and its loop deleted) before the error, so a failed `unlock` never leaves it open.
- udisks may need polkit authorization: in a remote or inactive session polkit answers `NotAuthorizedCanObtain`, and its textual agent asks on the terminal when there is one, which is why stdin stays inherited for every `udisksctl` call. When `check::polkit_asks` (pkcheck exit 2) says it will, `unlock` and `lock` first print which prompt wants what: `Passphrase:` the drive's, and polkit's `Password:` that of the account polkit names on its `Authenticating as:` line, which depends on the machine's polkit rules.
- Never run any of this against a real drive while working on it; test with a LUKS image made by `cryptsetup luksFormat` on a plain file, or `cryptsetup reencrypt --encrypt --disable-locks` on an ext4 image, which needs no root.

## age
- The plaintext lives only in `$XDG_RUNTIME_DIR/cryptkeeper/age/<hash of the real cipher path>/<real file name without .age>`, refused unless `$XDG_RUNTIME_DIR` is on tmpfs or ramfs. `age::private_dir` makes, or checks, every folder from `cryptkeeper` down to be a real folder (never a symlink) of this user's with mode 0700, at `unlock` and again before `lock` reads a copy; the copy is created with `create_new` and mode 0600 and filled from age's stdout, so a planted file or link is never followed. `<name>` beside `<name>.age` is a symlink to it. A file whose name does not end in `.age` is refused rather than given an invented name.
- `age::look` is the one reading of where the plaintext is (ck's copy, linked or not; a regular file at the view, with or without the copy; a dangling link; a link ck did not make), and `state`, `unlock` and `lock` all decide from it. `unlock` records the copy as it wrote it (inode, length, mtime) in `age/<id>.base` beside the copy's folder. A regular file at the view while the copy still exists, which is what an editor's atomic save over the link leaves, is encrypted when the copy is still as `unlock` wrote it or the two are identical; when both changed, `lock` refuses and names both, and never picks one. A regular file at the view of a vault in the list with no copy left (a logout after an editor saved over the link) reads `exposed`, and `lock` encrypts it and removes it; beside a vault that is not listed it is the user's own file and stays untouched.
- `lock` encrypts the plaintext to `.<name>.age.ck-tmp` beside the vault, checks it (header, exact payload length for that much plaintext, and with an identity a full decrypt compared byte for byte), syncs it, renames it over the vault, and only then deletes the plaintext and the link. Any failure leaves the old ciphertext and the plaintext both as they were, and says where the plaintext is. An `.age` file moved away while open keeps the vault `open`, and `lock` and `unlock` say to put it back.
- A passphrase file is encrypted again with `-p`, so `lock` and `init` ask for the passphrase twice, then print one ck line and decrypt the temp file, which asks once more, and compare it byte for byte with the plaintext before anything is renamed or deleted. That proof is what decides, because given an empty answer or a cancelled prompt both age and rage make up a passphrase and print it once, and Go age prints its prompts and that line on `/dev/tty`, where ck cannot read them; rage exits 0 having written nothing when its pinentry is cancelled, which is why every decryption's length is checked against the ciphertext's too. rage's stderr is relayed and watched for "autogenerated" as an earlier refusal; an identity file with `-e -i`, which encrypts to that identity's own key, so a file encrypted to more than one key is refused at `unlock`. An identity is stored only once it has decrypted the file, and `unlock -i` with another identity on a vault already open is refused, since `lock` would lock out the first one. Armored files are refused. `dead` is a link whose copy is gone (a logout or reboot empties `$XDG_RUNTIME_DIR`): `unlock` clears it and opens again, `lock` clears it.

## Demo rig
- `demo/stage.sh` builds an empty staged home in `demo/home` (HOME and every XDG variable pointed into it, run under `env -i`), with `$XDG_RUNTIME_DIR` at `/dev/shm/ck-demo-stage`, since age keeps an open file only on tmpfs; `down` removes both. The tapes give each section of the README its own picture, and there is no hero: `vaults.tape` renders `readme-assets/vaults.gif` (the list locking and unlocking a folder vault, then opening an encrypted file), `create.tape` renders `create.gif` (the create picker, a new folder's form, gocryptfs's prompts and master key), and `check.tape` the still `check.png` (`ck check`). `demo/render.sh` renders them in a container (the image is `demo/Dockerfile`, which adds gocryptfs and age), so a machine needs podman or docker and nothing else: `./render.sh` builds the release binary, then gives each tape a container of its own that stages, records and tears down, with `--device /dev/fuse --cap-add SYS_ADMIN` so gocryptfs can mount, never `--privileged`. The container has no syslog, so an unlock in frame takes the `-nosyslog` path, and no udisks, so the still's LUKS line shows the missing case.
- The tapes make and really mount vaults inside the stage with the password `demo`; master keys and the age key are throwaway. Each GIF opens on the TUI, not a prompt, and `down` still unmounts anything under the stage before its guarded delete.

## Build
- `cargo build --release`, binary at `target/release/ck`.

## Layout
- `src/main.rs`: the clap `Cmd` enum, the help screen's `WAYS` and `AFTER`, dispatch, `config_dir`, `state_dir`, `tilde` and `write_atomic`.
- `src/commands.rs`: one function per command, dispatching to a backend by `Kind`, with `unlock_one` and `lock_one` shared by `unlock`, `lock`, `edit`, `shell` and the terminal UI.
- `src/listing.rs`: the rows and the `--json` of `ls`, bare `ck` and the terminal UI.
- `src/tui/mod.rs`: the terminal UI's app, tabs and actions (`Action`, each with its `ck` command line), the event loop, and running an action with the terminal handed over.
- `src/tui/render.rs`, `src/tui/detail.rs`: the frame, footers and help panel; the panel beside the list.
- `src/tui/input.rs`: key dispatch. `src/tui/form.rs`: the create form and what a typed path plans (`Plan`). `src/tui/confirm.rs`: the gate in front of forget. `src/tui/alert.rs`: the alert.
- `src/tui/widgets.rs`: the words every key row is built from, the box parts, the footer and the scrollbar. `src/tui/line_edit.rs`, `src/tui/filter.rs`: editing a typed line, and `/`.
- `src/check.rs`: `ck check`.
- `src/completions.rs`: `ck completions` and the completers.
- `src/out.rs`: `say!`'s sink, captured while the terminal UI runs an action, with what the programs said and whether one was handed the terminal.
- `src/vault.rs`: `Kind`, `Vault`, `State`, `resolve` and `find`.
- `src/scan.rs`: the vaults found that the list does not hold, and where shell history opened a gocryptfs folder.
- `src/gocryptfs.rs`, `src/luks.rs`, `src/age.rs`: one backend each, with its `state`, `unlock` and `lock`.
- `src/registry.rs`: the vaults list.
- `src/mounts.rs`: `/proc/self/mounts` and `mountinfo`, `fusermount3`, the idle timeout, and who holds a busy view.
- `src/run.rs`: running a child at the terminal (`prompting`, `foreground`), with a time limit and no terminal (`bounded`), and quoting its stderr (`said`).
- `src/settings.rs`: `$XDG_CONFIG_HOME/cryptkeeper/settings`.
- `src/selfcmd.rs`: `self update` and `self check`, through `cargo install` and `cargo search`.
- `tests/readme.rs`: the README description block against `Cargo.toml`.
- `tests/cli.rs`: the built binary in an empty environment; its age tests need `age` or `rage` on `PATH` and a tmpfs temp folder, and fail saying so without them.
